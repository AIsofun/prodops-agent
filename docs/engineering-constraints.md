# Harness 工程约束

日期：2026 年 10 月 16 日。适用范围：从当前需求基线开始的后续开发。

本项目把 Harness 理解为让开发工作可理解、可执行、可观察和可验证的一组工程设施。它包含需求与设计入口、架构边界、开发命令、测试夹具、行为评测和检查反馈；它不等同于某一个框架，也不只是增加提示词。

这里侧重开发过程的 Harness。产品运行时的预算、取消、权限、确认和中断恢复属于另一层运行约束，已经分别纳入需求与架构；两层共同作用，但开发检查通过不能替代运行时保护。

本方案参考了将仓库知识作为事实来源、使用简短规则入口及机械检查维护架构的实践，并按当前小型项目规模裁剪。[Harness engineering 工程实践](https://openai.com/index/harness-engineering/)

## 1 分阶段工程要求

以下为本项目拟采用的工程基线。每条约束的实际落实状态见 [追踪表](traceability.md)；本文件写出了规则，不表示所有自动化都已经存在。

| 编号 | 工程约束 | 检查方式与生效阶段 |
| --- | --- | --- |
| HAR-001 | 需求有稳定编号和追踪记录，不能仅凭设计标记功能完成 | M0 使用文档检查脚本验证编号、映射、状态与证据引用 |
| HAR-002 | 仓库提供简短开发入口，能找到需求、设计、计划和检查方法 | M0 建立根目录 `AGENTS.md`，检查本地链接和入口内容 |
| HAR-003 | 模块依赖符合架构，领域逻辑与 Electron、HTTP、SDK 解耦 | M1 建立 Python 导入边界和 TypeScript 依赖规则；以允许和禁止的导入样例验证检查器 |
| HAR-004 | API、事件和 IPC 契约一致，边界输入运行时校验 | M1 生成 OpenAPI 和 TS 客户端，CI 检查生成漂移；针对非法输入与版本不兼容测试 |
| HAR-005 | 环境与检查可复现，只有存在的命令才写入操作说明 | M1 锁定 Python/Node 依赖并建立统一检查入口，分别报告通过、失败与未执行 |
| HAR-006 | 诊断测试与模型评测分开，反馈面向行为而非固定文案 | M2 建立确定性 mock 场景，M4 补真实模型评测记录；两个部分均有证据后才验证本项 |
| HAR-007 | 关键故障可以重现并核对，不通过隐藏错误使测试通过 | M2 起覆盖重复请求、断线、取消、崩溃、未知动作和并发边界；功能增加时补充相应故障样例 |
| HAR-008 | 桌面与安装包有实际运行证据 | M3 起验证主进程桥接、界面流程、进程退出及干净 Windows 安装，保留必要截图或日志 |
| HAR-009 | CI 按改动范围运行检查，发布使用完整检查 | M1 接入当前代码托管平台的 CI；实现阶段未配置的检查明确为未接入，关键检查失败不能作为可发布版本 |
| HAR-010 | 开发按需求切片，变更与例外可追踪 | M0 起每次功能变更关联需求，更新代码与证据位置；架构例外登记原因、影响和退出条件 |

## 2 需求与设计的职责

[需求文档](requirements.md) 说明用户需要什么与如何验收；[架构文档](architecture.md) 说明如何实现；[实施计划](implementation-plan.md) 说明顺序；[追踪表](traceability.md) 说明当前事实。需求与设计冲突时先辨明来源并同步文档，不能悄悄删减需求或把架构偏好当成用户确认。

`AGENTS.md` 只放导航和日常开发约束，详细规则留在对应文档。后续使用不同开发工具或人工开发时也遵循同一套工程规则。此入口不授权外部发布、发送消息或真实设备操作。

## 3 架构与契约检查

Python 允许的业务依赖方向为 `api → application → domain`，`runtime` 使用应用服务、领域接口和 Agent；适配器实现领域或应用接口，启动层负责装配。领域层不得导入 FastAPI、Electron 或具体模型 SDK；前端组件不得访问数据库或 Python 进程。

导入边界检查必须解析模块关系或使用成熟工具，不能靠搜索几个字符串冒充可靠约束。DTO 生成后检查仓库是否出现差异；修改事件含义、字段或版本时同步生产者、消费者和兼容性用例。对模型输出、IPC 参数和外部工具结果执行运行时校验。

## 4 检查入口与执行范围

当前统一检查入口分为文档、工程设施与 M1 产品静态检查：

```text
python scripts/check.py --profile docs
python scripts/check.py --profile harness
python scripts/check.py
```

docs 使用 Python 标准库检查需求追踪、任务依赖和交付回执。harness 增加环境、Python/TS 工具代码类型与检查器回归；默认 m1 再连接真实产品的类型、边界和契约检查。缺少产品代码或契约返回 NOT_READY，不以零文件或夹具通过冒充产品通过。安装与完整范围见 [质量工作流](quality-workflow.md)。

统一入口已经覆盖工程设施及预定产品的环境、类型、导入边界与生成结果比较；格式检查、产品行为、消费者和运行测试随相应代码建立。文档变更运行 docs；任务核心变更运行状态和持久化测试；接口变更运行契约与消费者测试；界面变更运行相应界面流程；发布运行双数据库、打包和关键端到端验证。低影响文案修改不要求新增产品测试。

依赖版本、锁文件和工具版本随实现一起维护。CI 的“必需检查”是否开启，需要在实际托管平台验证；本地脚本通过不能写成远端 CI 已通过。

## 5 测试与模型行为评测

确定性检查使用明确的输入、mock 模型决策、工具结果和预期状态，不访问真实设备，不要求模型给出逐字相同的回复。测试覆盖真正的业务约束，避免只复制实现细节。[测试分层实践](https://martinfowler.com/articles/practical-test-pyramid.html)

模型评测记录模型标识、配置版本、场景集、实际工具轨迹、结果和错误。重点检查证据支持、工具与参数合法性、权限范围、不确定性表达、失败处理，以及任务是否在预算内停止。数值与规则可自动评分，诊断合理性等语义项保留人工评阅。

起始场景包括相机掉线、OCR 质量下降、Kafka 堆积和推理延迟；再加入正常状态、缺失数据、工具失败、错误参数、模型不可用、歧义问题和日志中夹带指令等反例。模拟场景回归通过不代表实际模型或现场设备验收通过，评测分数也不能证明系统整体安全。

真实模型评测需要明确服务、数据边界和费用范围。测试数据不默认上传到外部服务。工程规则不因需要模型评测而自动授权外部账号或现场设备访问。

## 6 故障和桌面验证

故障注入优先发生在模拟连接器和隔离数据库。记录中断点、已提交状态、外部模拟结果和恢复后的行为，以验证重复提交不重复排队、事件不丢失，以及未知写操作不会自动重试。

桌面验证覆盖首次启动、连接切换、排查进度、证据查看、错误、取消、重连、托盘与退出。开发模式验证和安装包验证分开保存；安装包需在没有开发运行环境的 Windows 电脑或干净虚拟机上执行。安装成功不代表已通过真实模型、服务器或现场连接器验证。

## 7 完成标准与例外

“已实现”至少需要存在实现位置，并说明未完成的验收；“已验证”必须有可读取的验证记录，列出命令或步骤、环境、结果和适用范围。一次检查可以覆盖多个需求，但不能把同一张成功截图当作全部故障场景的证据。

跳过、未运行或基础设施不可用，统一如实记录，不能标为通过。影响交付的缺口保留在追踪表。确有必要暂时违反某项架构或检查规则时，在 `docs/decisions/` 新建记录，包含关联编号、理由、影响、补偿措施和退出条件，并在追踪表引用；按当前任务已有授权推进，不增加一律重新向用户请示的流程。

当前已落地文档导航、追踪、阶段任务、交付回执、统一入口和检查器。真实产品代码及契约接入、模型评测、桌面运行和 CI 仍在对应任务建设。代码复核与验证采用 [统一模板](quality-workflow.md)，自查与独立复核明确区分。
