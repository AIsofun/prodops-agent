# 智能制造桌面 Agent 需求文档

日期：2026 年 10 月 16 日。版本：1.0。状态：用户已确认需求基线，新桌面产品尚未实现。

用户已整体确认本需求文档，后续按本基线安排开发与验收。来源栏保留编制时的来源记录；“推导”项已经随本次整体确认纳入基线，不再代表尚未获确认。性能数值、现场协议、目标系统版本等明确列为待确定的参数，仍需在对应实现或验收前补齐。

本产品为制造现场的操作员和运维人员提供可以双击打开的异常排查桌面软件。用户描述问题后，系统查询授权范围内的设备、指标、日志和操作手册，持续展示进度，并给出带证据的诊断及处置建议。产品同时支持本机运行和连接工厂内网服务器。

需求是后续设计和验收的依据。每项需求使用稳定编号，具体实现和验收状态统一记录在 [需求追踪表](traceability.md)。现有 demo 只提供业务样例，不能据此认定新产品已经完成相应需求。

## 1 需求来源与范围

来源栏中的“已确认”表示编制前已有用户明确选择；“推导”表示编制时为形成可用产品而补充，现已随整体确认纳入基线；“待定”表示部分参数仍不能形成完整验收标准。优先级 P0 是对应交付阶段的必要项，P1 为后续增强，P2 为远期扩展。P0 不表示所有功能都要在第一个开发阶段完成。

已经确认的技术与平台约束：

- 界面采用 React、TypeScript 和 CSS，桌面框架采用 Electron，业务服务主要采用 Python。
- 同时支持 Agent 在操作员电脑运行，以及在工厂内网服务器运行。
- Windows 桌面端优先，后续扩展 macOS 和 Linux。
- 可以重新设计和编码现有项目，代码复用不构成约束。
- 先整理需求，用于后续追踪实现，再据此校准架构和实施计划。

本需求基线先交付双模式诊断版本，再接入现场连接器与真实处置。大规模设备监控平台、视频墙、MES 全量功能、跨工厂历史自动同步、多 Agent 编排和默认自动修复不属于首版承诺。

## 2 使用者与关键流程

| 使用者 | 主要任务 |
| --- | --- |
| 操作员 | 描述异常、查看进度与证据、理解建议、按权限确认操作 |
| 运维人员 | 配置连接、排查服务和设备、核对处置效果、查看历史 |
| 管理员 | 配置工作区与权限、模型和连接器、备份与版本升级 |

本机流程为“打开软件 → 自动准备本机服务 → 配置或选择模型 → 描述异常 → 查看排查与结果”。服务器流程为“打开软件 → 选择工厂服务器并登录 → 选择工作区 → 描述异常 → 查看排查与结果”。

模型位置独立于 Agent 位置。本机运行 Agent 不等于必须在本机运行模型；连接服务器也不等于能直接访问操作员电脑上的文件或设备。

## 3 功能需求

### 3.1 软件启动与部署

| 编号 | 来源与优先级 | 需求与验收标准 |
| --- | --- | --- |
| REQ-001 | 已确认 P0 | 提供 Windows 桌面应用。安装后通过快捷方式双击打开独立窗口；目标用户无需打开终端或自行启动网页。安装包包含所需应用运行环境，在未安装开发用 Node.js/Python 的验收电脑上可启动。 |
| REQ-002 | 已确认 P0 | 支持本机 Agent。选择本机模式后自动准备业务服务；服务不可用时说明原因。关闭窗口、明确退出和重新打开的行为可预测，不遗留无法管理的后台进程。 |
| REQ-003 | 已确认 P0 | 支持内网服务器 Agent。客户端可配置服务器地址并连接；服务器独立运行。退出客户端后已提交的服务器任务继续，重新连接可查看。 |

### 3.2 对话与排查任务

| 编号 | 来源与优先级 | 需求与验收标准 |
| --- | --- | --- |
| REQ-004 | 推导 P0 | 提供会话列表和多轮交流。在同一会话追问时使用有权限的历史上下文；新会话不混入其他会话记录。忙碌期间的新输入不会意外启动冲突任务或丢失。 |
| REQ-005 | 推导 P0 | 排查作为独立任务执行。提交后显示任务编号或可追踪入口，随后持续显示排队、执行步骤和最终状态，不能只在最后一次性返回结果。 |
| REQ-006 | 推导 P0 | 诊断提供证据。结论关联实际工具结果、采集时间和来源；可查看授权范围内的原始结果。未采集到的信息不能伪装成工具事实；任务完成与故障已解决分别显示。 |
| REQ-007 | 推导 P0 | 保存会话、任务与结果。重启客户端后可找到历史记录；查询按权限和当前连接隔离，支持分页。 |
| REQ-008 | 推导 P0 | 断线后补看进度。客户端短暂断开不会直接使服务器任务失败；重连后补齐已产生的事件或恢复完整快照，界面不重复展示同一事件。 |
| REQ-009 | 推导 P0 | 支持取消任务。取消后不再安排后续步骤；已完成的操作仍保留，在途操作不能被错误显示为已撤销。 |
| REQ-010 | 推导 P0 | 中断后的结果可核对。服务异常退出后，未确认结果明确标为待恢复或待核对；真实写操作不得因重启或重连被盲目重做。 |
| REQ-019 | 推导 P0 | 执行有预算和并发限制。可限制运行数量、排队、工具调用次数、超时和等待确认时间；超限返回明确状态，不能无限执行或悄悄重置预算。具体初值由架构与实测决定。 |

### 3.3 模型与工业系统

| 编号 | 来源与优先级 | 需求与验收标准 |
| --- | --- | --- |
| REQ-011 | 推导 P0 | 支持真实模型及显式模拟模式。可配置模型服务，至少完成一种实际协议的接入；模型不可用时如实报错，不自动切换 mock 冒充实际结果。无模型时可显式使用模拟场景演示。 |
| REQ-012 | 推导 P0 | 工具与工业连接器可以扩展。先通过模拟场景验证链路，再以至少一个现场只读连接器验证真实排查；新增连接器不要求重写界面。设备协议与现场系统名单待确定。 |
| REQ-013 | 推导 P0 | 连接配置和数据分开。可保存、选择本机或工厂服务器配置；切换后显示正确的服务与工作区，缓存、事件和凭据不串用，既有任务仍归原连接所有。 |
| REQ-015 | 推导 P1 | 支持显式添加附件。操作员选择文件后可上传或导入当前部署；任务能引用该附件。没有授权的本地路径不能被服务器自行读取。文件类型和大小上限在实现前确定。 |

### 3.4 身份与处置

| 编号 | 来源与优先级 | 需求与验收标准 |
| --- | --- | --- |
| REQ-014 | 推导 P0 | 服务器使用身份和权限控制。未登录、令牌失效、跨工作区和越权设备访问均由后端拒绝；本机服务也限制访问者。具体企业身份提供方后续选择。 |
| REQ-016 | 推导 P1 | 写操作采用具体提案和确认。用户能看到目标、参数、影响和有效期；后端验证权限及确认。重复点击不会重复调度同一提案，修改参数后原确认失效。该要求是开放任何真实写操作的前提。 |
| REQ-017 | 推导 P1 | 处置后独立验证结果。分别记录操作是否提交成功和故障是否恢复；未知结果需要核对，同一设备的冲突操作受控。没有完成此需求前不宣称自动修复已经可用。 |

### 3.5 异常与交付

| 编号 | 来源与优先级 | 需求与验收标准 |
| --- | --- | --- |
| REQ-018 | 推导 P0 | 用户能理解异常状态。服务未就绪、模型未配置、无权限、网络中断、工具失败、任务失败和结果待核对有区分，并提供可采取的下一步。错误不暴露凭据。 |
| REQ-020 | 推导 P0 | 数据可备份恢复。分别验证本机和服务器的会话、任务、附件与必要凭据恢复流程；恢复记录说明适用版本和结果。 |
| REQ-021 | 推导 P0 | 安装与升级可管理。明确版本和协议兼容范围；升级前妥善处理任务和数据，不兼容时阻止错误执行并提示。首版支持内网离线安装与升级，不以外网下载为必需条件。 |

## 4 非功能需求

| 编号 | 来源与优先级 | 需求与验收标准 |
| --- | --- | --- |
| NFR-001 | 推导 P0 | 两种部署的核心体验一致。同一组诊断场景在本机和服务器均能执行；差异只来自权限、连接和资源条件，不能出现只支持某一模式的核心流程。 |
| NFR-002 | 推导 P0 | 保护凭据与数据边界。界面不获得模型密钥或通用本地执行权限；日志、事件和导出内容脱敏；证据和附件读取校验归属。 |
| NFR-003 | 推导 P0 | 问题可定位。通过关联编号定位请求、任务和工具步骤；能区分模型、连接器、存储、身份与客户端问题，记录必要耗时和错误，不依赖保存模型内部思维。 |
| NFR-004 | 推导 P0 | 数据和重复请求的行为一致。重复提交、并发任务和状态更新保持约束；分别在本机和服务器数据库验证，不因换数据库就破坏任务或事件规则。 |
| NFR-005 | 待定 P1 | 建立性能基线。测量干净 Windows 环境的冷启动、内存、首条进度、事件延迟和任务吞吐；记录硬件、数据量、模型耗时及百分位。数值门槛在基线后确定，确定前不能宣称性能验收通过。 |
| NFR-006 | 已确认 P0 | 需求可追踪。每项需求关联设计、实施阶段、代码位置和验收证据；状态可区分未开始、进行中、已实现和已验证。仅编写了设计不算功能完成。 |

## 5 交付边界

开发阶段 M0 至 M6 的任务在 [实施计划](implementation-plan.md) 定义，需求对应阶段在 [追踪表](traceability.md) 维护。

- M0 完成需求、追踪和工程规则的最小基础。
- M1 至 M4 形成 Windows 双模式诊断版本，允许使用模拟工业数据验证，同时验证真实模型和服务器权限。
- M5 接入实际只读工业系统；真实写操作按需求前提单独开放。P1 附件或写操作不阻碍只读诊断版本交付，不能作为已实现功能宣传。
- M6 完成相应发布范围的安装、升级和备份恢复验收。交付范围外的 P1 项继续保留在追踪表。
- macOS/Linux 桌面支持为 P2 后续范围；Python 服务器支持 Windows/Linux 是当前架构建议，实际平台组合在发布验证中确认。

## 6 待确定事项

| 事项 | 当前处理方式 | 最晚明确时间 |
| --- | --- | --- |
| 首个现场系统、设备协议和只读 API | 先使用现有故障样例，连接器接口保持独立 | 实施真实连接器前 |
| 真实模型及协议 | 优先评估当前项目已有的本地或内网兼容服务 | M4 真实模型验收前 |
| 工作区、角色与企业身份源 | 首版按有限工作区和角色设计，预留企业登录适配 | M4 身份功能实现前 |
| Windows 版本、CPU 架构和验收电脑 | 先围绕当前 Windows 开发环境设计，不据此承诺所有系统版本 | M3 打包验收前 |
| 数据保留时间、附件上限和恢复目标 | 作为部署策略配置，避免写成没有依据的固定数值 | 对应功能实现前 |
| 性能阈值 | 先测量并登记，再形成验收门槛 | 性能需求进入已验证前 |

## 7 需求变更规则

编号一经使用不重新分配。新增需求分配新编号，取消或延期的需求保留原编号和原因。修改范围或验收标准时，同步更新追踪表、受影响的设计及实施计划。技术方案调整不得把已经确认的产品需求静默删除。

需求基线的确认与实现状态互不替代。来源栏保留历史，不把后续新增的推导项自动视为已确认；变更应记录是否纳入当前基线。涉及新增外部系统、权限或范围的选择在实施前澄清。
