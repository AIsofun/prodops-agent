# 编码 Agent 厂商实践调研：Anthropic、GitHub、Cursor

调研日期：2026-10-16。本文供综合报告引用，不修改当前项目需求或工程规则。

## 证据边界

- 本文实际打开了下列官方网页，未把搜索摘要作为唯一依据。
- **厂商建议**：产品官方给出的使用方法，不等于独立证明其效果。
- **第一方经验**：厂商对内部或用户实践的总结，存在产品和团队背景限制。
- **项目推断**：根据来源提出的适配建议，需要本项目验证。
- 本次未纳入独立实证研究，因此不对生产率、缺陷率改善幅度作结论。
- 多家建议出现共同方向，不能据此宣称存在统一行业标准。
- 产品行为与默认权限会变化；落地时需复核所用版本和组织配置。

## 1. Anthropic：把验证闭环交给 Agent

**厂商建议**：提供可运行的测试、构建或截图比较，让 Agent 根据结果迭代；复杂工作先探索和计划，小修复可直接实现。[Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices)

**厂商建议**：常驻上下文只保留项目特有命令、约定和陷阱；偶尔使用的知识按需加载。必须发生的动作交由 hook 等确定性机制执行。[同一来源](https://code.claude.com/docs/en/best-practices)

**第一方经验/建议**：用独立上下文审查实现，检查需求遗漏和正确性；审查意见也可能诱导过度设计，应核实真实影响。[同一来源](https://code.claude.com/docs/en/best-practices)

**项目推断**：任务完成信号应是可检查的行为证据，而非 Agent 自述成功。

**项目推断**：不把“每次改动都新增测试”设为机械规则；测试投入与业务影响相匹配。

## 2. Anthropic：子代理适用于边界清楚的旁支任务

**厂商说明**：子代理具有独立上下文和受控工具，适合隔离大量搜索、日志或文件阅读；其请求同样消耗账户额度。[子代理文档](https://code.claude.com/docs/en/sub-agents)

**项目推断**：调研、只读审查、独立测试分析可作为候选；紧密依赖的连续实现不必拆给多个代理。

**项目推断**：委派必须给出输入、输出、允许修改的文件、验证要求和汇总责任人。

**项目推断**：子代理完成不等于整项任务完成，集成后仍需统一检查。

## 3. Anthropic：自然语言约束之外还要有执行边界

**厂商说明/建议**：权限配置控制动作，沙箱限制文件与网络访问；不可信文本可能包含提示注入。敏感改动和 MCP 接入需要审查，建议使用可信服务与隔离环境。[安全文档](https://code.claude.com/docs/en/security)

**项目推断**：AGENTS.md 用来说明规则，操作系统权限、网络限制和 CI 用来执行规则。

**项目推断**：开发环境不授予生产设备写权限；真实设备接入测试需要单独授权的环境。

## 4. GitHub：把 Issue 写成可验收的任务

**厂商建议**：任务包含问题、验收条件和相关位置；先从范围较小的修复、界面调整或文档等任务开始。复杂、模糊和敏感工作不宜直接整包委派。[任务最佳实践](https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results)

**厂商建议**：可以先研究、计划、在分支迭代，再开 PR；仓库指令应说明构建、测试和验证方式。审查反馈可批量提交，减少碎片化重做。[同一来源](https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results)

**项目推断**：本项目实施阶段需要进一步拆成需求切片，里程碑本身不适合作为单次编码任务。

## 5. GitHub：环境配置是交付能力的一部分

**厂商说明**：可用仓库内 setup workflow 预装工具和依赖，减少 Agent 临时猜测。一个初始化步骤失败后，剩余步骤可能跳过，Agent 仍会在当前环境继续工作。[开发环境配置](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)

**项目推断**：应另设明确的环境就绪检查；环境失败不能自动解释为产品失败，也不能将未执行测试写成通过。

**项目推断**：本地、Agent 工作环境和 CI 使用相同的检查入口，并记录依赖与运行时版本。

## 6. GitHub：AI 审查需要验证

**厂商说明/建议**：AI 审查可能漏报、误报或提出错误修复，应补充人工审查并测试生成代码；云端 Agent 默认有隔离环境及网络防火墙。[责任使用说明](https://docs.github.com/en/copilot/responsible-use/agents)

**项目推断**：实现 Agent 与审查 Agent 分工有帮助，但两者同意不能替代验收标准和运行证据。

**项目推断**：审查发现须附具体位置、触发条件、影响和复现依据；误报有理由关闭，无需为了让审查“有产出”添加抽象。

## 7. Cursor：计划、测试与隔离并行

**第一方经验/厂商建议**：复杂工作先计划，简单改动可直接做；其 TDD 示例先确认测试失败，再要求实现通过，避免为缺失功能造假实现。[Agent 编码最佳实践](https://cursor.com/blog/agent-best-practices)

**厂商说明**：并行 Agent 可使用独立 worktree，完成后再集成；生成代码仍需阅读 diff 和复核。[同一来源](https://cursor.com/blog/agent-best-practices)

**项目推断**：可并行的是独立工作，不是同一份共享文件上的无协调写入。

**项目推断**：多个方案竞争属于可选实验方式，成本、集成和验证负担需一并衡量。

## 8. Cursor：规则从真实失败中生长

**厂商建议**：规则应具体、聚焦并限定范围；引用代码实例，避免重复整份指南。格式规范交给 linter，观察到重复错误后再补规则。[规则文档](https://cursor.com/docs/rules)

**项目推断**：保留一个简短入口，专题内容放到链接文档；不要为每个编码产品复制多套独立治理正文。

**项目推断**：新增规则同时说明它针对的真实问题、检查方式和维护位置。

## 9. Cursor：云端环境默认值不能类推

**厂商说明**：Cloud Agent 自动运行终端命令，存在提示注入与数据外传风险；互联网默认开启，可配置域名白名单及组织限制。[云端安全说明](https://cursor.com/docs/cloud-agent/security)

**项目推断**：不能把“云端”或“沙箱”当作完整安全结论，应实际核对外网、凭据、持久化数据和工具权限。

**项目推断**：本项目提交给外部 Agent 的资料使用脱敏样本，生产日志和密钥不作为默认上下文。

## 10. 面向本项目的候选工作流程

以下为项目推断，尚未成为已确认工程制度。

| 步骤 | 最小输入 | 交付证据 | 不满足时的处理 |
| --- | --- | --- | --- |
| 任务就绪 | 需求编号、行为、边界、验收 | 一份范围清楚的任务描述 | 澄清关键缺口，继续无依赖工作 |
| 了解现状 | 入口文档、相关实现、既有检查 | 相关模块与风险摘要 | 避免凭猜测跨层改造 |
| 制定切片 | 变更范围、接口、验证方法 | 小计划及明确不包含的工作 | 大改动进一步拆分 |
| 环境核验 | 依赖、运行时、隔离数据 | 环境检查结果和基线失败 | 标明环境阻塞，不伪造通过 |
| 实现 | 计划、允许的文件边界 | 可审查 diff | 越界范围单独记录理由 |
| 验证 | 验收条件、回归范围 | 命令结果、行为结果、必要截图 | 修复根因后重跑相关检查 |
| 独立复核 | diff、需求、证据 | 有依据的问题清单 | 核实误报，修复实际缺陷 |
| 集成 | 全部相关修改 | 集成检查、追踪更新 | 冲突解决后再次验证 |
| 发布验收 | 安装包和目标环境 | Windows 实际运行证据 | 未验收部分不得记为交付 |

建议任务描述固定包含下列字段：

```text
关联需求：REQ / NFR / HAR 编号
目标行为：用户在什么条件下得到什么结果
范围：本次包含与不包含的内容
参考：设计章节、相关代码、已知问题
验证：可执行检查与验收场景
执行边界：隔离数据、外部服务、写操作授权范围
完成报告：修改位置、验证结果、未验证范围、遗留项
```

## 11. 不宜直接变成硬性规范的做法

- **项目推断**：每个任务必须详细计划，会增加低影响改动的成本。
- **项目推断**：每个任务必须多代理，会增加上下文交接和集成工作。
- **项目推断**：只要测试通过就可交付，会遗漏验收标准未覆盖的行为。
- **项目推断**：无限次修复直到所有审查意见消失，会诱发无关改造。
- **项目推断**：无限扩大 AGENTS.md，会削弱规则的可读性与可维护性。
- **项目推断**：依赖提示词约束生产操作，无法代替权限和执行隔离。

## 12. 建议先收集的效果数据

以下为项目推断，用于检验流程是否有效，不代表厂商统一标准。

- 从任务开始到得到可验收改动的时间，区分等待环境与实际开发。
- 首次检查失败、集成失败和安装失败的原因分布。
- 人工审查发现的问题，以及 Agent 审查中被证实的误报。
- 已交付需求的返工和缺陷逃逸情况，关联具体任务。
- 单任务 Agent 使用成本与并行数量，避免只统计生成代码量。
- 因缺失文档、错误规则或运行环境问题造成的重复失败。
